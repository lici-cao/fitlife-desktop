# P5 改造说明：科学性可溯源、动作库寻源与食谱方案

> 本文件对应改造阶段 **P5（周期 2 周 / 10 人日）**，在 P1–P4 之上继续叠加。
> 目标：回答三个问题——**① 生成的计划凭什么算科学？② 动作库的内容能不能寻源、新内容怎么审？③ 动作与饮食都要标注来源与热量单位。**
> 对应报告表 13 的 P5 行，清偿差距 **G1（生成链条缺知识约束与可解释性）**、**G2（无规则校验证据）**、**G9（数据无出处）**。

---

## 一、三个问题的正面回答

### 1.1 生成的计划有科学性吗？

有，但要说清楚"科学性来自哪里"。它不是"大模型说它对"，而是三件事叠起来：

| 层次 | 机制 | 代码位置 |
| --- | --- | --- |
| 参数层 | BMI / BMR（Mifflin-St Jeor）/ TDEE / 目标热量（减脂 −400、增肌 +300）/ 心率储备与 Karvonen 靶心率（50–70% HRR，上限 90%）| `util/BodyMetrics.java` |
| 规则层 | 六类硬约束：靶心率区间、FITT-VP 频率与周有氧量、周容量环比 ≤10%、同肌群间隔 ≥48h、禁忌症分级、单次容量预算（4–6 动作 / 超时 ≤15% / 单肌群周组数 ≤20）| `service/PlanValidator.java`、`knowledge_rule` 六条 |
| 证据层 | 每个计划附 `references`（指南 / 知识条目 / 动作来源 / 食物数据源，含发布方、链接、证据等级、用在哪）+ `scienceNote` 说明依据与局限 | `service/ReferencesService.java`、`PlanSupport.scienceNote` |

**为什么这套组合比"纯大模型生成"更可信**：模型的输出被夹在"知识条目约束 → 结构化 JSON → 规则校验器 → 最小修复"中间，任何越界都会被校验器抓住并以 `WARN/ERROR + 具体动作名 + 具体数值`回显；同时每条动作都能点到出处。也就是说——**可解释、可复核、可复现**，而不是"看着挺合理"。

**证据基座（写进 `references` 的五条固定来源）**：

| 编号 | 来源 | 用于 |
| --- | --- | --- |
| ACSM-11 | ACSM's Guidelines for Exercise Testing and Prescription, 11th ed. | FITT-VP 编排、靶心率区间、禁忌症 |
| COMPENDIUM-2024 | 2024 Adult Compendium of Physical Activities（pacompendium.com） | MET 值与热量估算 `kcal = MET × kg × h × 1.05` |
| NSCA-4 | NSCA's Essentials of Strength Training and Conditioning, 4th ed. | 组数/次数/组间休息/RPE、同肌群 48h |
| WHO-2020 | WHO Guidelines on Physical Activity and Sedentary Behaviour (2020) | 每周 ≥150 分钟中等强度有氧 |
| CFCT-6 | 中国食物成分表（第 6 版） | 食物热量与三大营养素（kcal/100g） |

> 边界：这是**健康与亚健康人群的通用运动处方**，不是医疗诊断；`scienceNote` 末尾强制声明"不替代医生或注册营养师"，有伤病史以禁忌提示与医嘱为准。

### 1.2 动作库能不能寻源？新内容怎么审？

**能寻源**：`exercises` 每条都有 `source_type / source_title / source_url / source_page / evidence_level / last_verified_at`。100 条动作全部已回填（覆盖率 100%），前端在动作库列表和计划明细里都能直接点开原文。

**新内容怎么进来**（两条路，都不允许"直接写库"）：

1. **用户投稿** → `exercise_submission`（状态 `PENDING`）
2. **管理员审核** → 通过才写入 `exercises`（`review_status='APPROVED'`），驳回必须写原因

**审核审什么**（这是关键，`GET /api/admin/exercise-submissions` 会把口径一起返回）：

| 审什么 | 具体判定 | 谁来做 |
| --- | --- | --- |
| ① 可溯源性 | 来源链接必填且为 `http(s)`、能打开、来源类型（GUIDELINE/TEXTBOOK/JOURNAL/DATABASE/COMMUNITY）与证据等级（A/B/C）匹配 | 机器（自动） |
| ② 与来源一致 | 该动作确实出现在这份指南/教材的对应章节（`source_page`），名称、要领、禁忌与原文不矛盾 | 人工 |
| ③ 领域参数合理 | MET 在 1–20、难度 1–3、类别/肌群/器械在枚举内、动作说明 ≥8 字、重名阻断 | 机器（自动） |

**所以审的不是"这个动作有没有效"这种无法判定的问题，而是"它有没有出处、出处对不对得上、参数是否落在生理合理区间"**。平台不为第三方结论背书，只保证"用户看到的每一条都可追溯到公开来源，且没被改坏"。自动校验不通过的投稿直接落 `REJECTED` 并写明原因，不进人工队列。

### 1.3 动作来源链接 + 计划含饮食（标注热量单位）

- **动作**：计划明细项带 `sourceUrl / sourceTitle / evidenceLevel / sourcePage`，前端展示为可点链接 + 证据等级标签。
- **饮食**：计划新增 `dietDays`（7 天 × 早/午/晚 + 训练日加餐），每条食物给：`kcal`（千卡）、`grams`（可食部克数）、`unitLabel + amountDesc`（家常单位，如"1 碗(150g)"）、`proteinG/carbG/fatG`、`sourceUrl`。热量口径统一为 **kcal**，页面底部固定说明"克数为可食部重量"。
- **目标值计算**：目标热量取 `BodyMetrics.targetCalories`；蛋白按 `DIET_TARGET.proteinPerKg`（减脂 1.8–2.2、增肌 1.6–2.0、健康 1.2–1.6 g/kg 取中值）；脂肪 = 热量 × 25% ÷ 9；碳水吃余量 ÷ 4。餐次分配 30/40/30，训练日加餐约 8%。

## 三、数据库变更（V5__p5_sourcing_diet.sql，幂等）

## 五、对既有逻辑的影响

- **生成链路**：仍走 P2 的 15 步主链路；饮食与引用是"生成成功后的增量装配"，失败只 `warn` 降级为空，不影响计划主体。
- **旧接口**：`/api/data/*`、`/api/chat/*`、`/api/ai/*` 全部未改签名；`FoodController`、`ExerciseController` 只增不改。
- **动作库**：候选查询改为 `findApprovedCandidates`（只取 `APPROVED` 或历史 NULL），未审核投稿不会进入生成候选集，避免"投稿即生效"。
- **前端**：新增页面与菜单项只对 ADMIN 可见；`localStorage.fitlife_role` 仅用于显示，权限仍由后端 `hasRole('ADMIN')` 判定。

## 七、回滚方案（由内到外四层）

1. **前端回滚**：删除 `/admin/review` 路由与菜单项，计划页隐藏"饮食方案/引用"卡片——后端多返回的字段前端不读即可。
2. **接口回滚**：`SecurityConfig` 中移除 `POST /api/exercise/submit`、`GET /api/exercise/my-submissions`、`GET /api/food/**` 三条规则，重启即恢复旧白名单。
3. **功能回滚**：`PlanOrchestrator` 中注释 ⑫b 段（饮食 + 引用装配），计划恢复为"只有动作"的形态；`diet_enabled` 列保留但不再写入。
4. **数据回滚**：V5 只做"加列 + 建表 + 回填"，不删不改既有列；如需彻底还原，`DROP TABLE exercise_submission, diet_plan_item, food_item;` 并 `ALTER TABLE exercises DROP COLUMN ...`（12 列）。旧版本计划数据不受影响。

## 八、工程注意事项（踩过的坑）

1. **`.ps1` 必须 UTF-8 带 BOM**：write 工具默认无 BOM，PS 5.1 会按 GBK 解析中文导致"字符串缺少终止符"，改完要用 python 以 `utf-8-sig` 重存。
2. **PS 5.1 的 `HttpWebRequest` 才能读 4xx 响应体**：`Invoke-WebRequest` 在 4xx 时拿不到 body，验证脚本统一用 `System.Net.HttpWebRequest` 手写封装。
3. **mysql 客户端参数不能拆**：`@("-h", $host)` 会让 host 只收到 `127`，必须写 `"-h$DbHost"`。
4. **`Win32_Process.Create` 不继承当前会话的环境变量**：用 WMI 脱离作业树启动后端时，`DB_URL/DB_USER/DB_PASS` 必须显式写成 `--spring.datasource.*` 参数，否则会静默连到 `localhost:3306` 并报 `Communications link failure`。
5. **测完不要 `job_kill` 掉启动后端的那条作业**：job 的进程树会连带杀掉 java 与 mariadbd；本机验证用 `WMI Create` 起独立进程。
6. **引用去重按 URL 而非标题**：同一本指南对应多个动作时，按标题去重会把同一条来源重复列出（曾导致 8 条变 20 条），改为 `URL|url` 去重并合并 `usedFor`。
7. **审核口径不要写成"审核真伪"**：平台能做的是"来源可定位 + 参数合理"，替第三方结论背书既做不到也不该做，文案与文档都按此表述。
