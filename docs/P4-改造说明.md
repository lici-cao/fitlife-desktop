# P4 改造说明：执行闭环与统计

> 本文件对应改造阶段 **P4（周期 2 周 / 10 人日）**，完全覆盖 P1/P2/P3 的全部修缮内容。
> 目标：把「生成计划 → 训练 → 记录」打通成闭环，让 Dashboard 的数据来自数据库而不是浏览器本地存储。
> 对应报告表 13 的 P4 行，清偿差距 **G6（统计在前端自算）** 与 **G7（打卡重复与丢更新）**。

| 对象 | 变更 | 说明 |

## 四、关键实现说明

### 1. 教练口径统一在服务端
前端原来用 Harris-Benedict 且减脂取 −500 kcal，后端 `BodyMetrics` 用 Mifflin-St Jeor 且减脂取 −400 kcal，同一份档案会得出两个目标热量。
P4 改为：服务端返回 `targetCalories`，前端 `stores/user.ts` 的 `targetCalories` computed 优先使用 `serverTargetCalories`（由 `syncTargetCalories()` 注入），本地公式只作为接口不可达时的兜底。

### 2. 应做数（分母）的三种情形
`DailySummaryService.resolvePlanFor()` 用显式循环实现，按顺序取：
1. 当天 = 今天 → 优先 ACTIVE，退最近一版（覆盖「今天生成、今天打卡」）；
2. 取创建日期不晚于当天的最近一版（历史日期当时的真实口径）；
3. 当天早于全部版本 → 空（不能把未来才有的安排算成历史应做项，否则依从率被凭空压低）。

在此基础上 `refreshDay` 加两条补偿：
- **跨周补打卡**：当天打卡的动作属于计划里另一天 → 把那个计划日的全部动作计入应做数（否则练了却算没练）；
- **补打历史日**：历史日期解析不到版本、但当天确有打卡记录 → 借当前 ACTIVE 版本算分母。

### 3. 打卡后的聚合在同一事务内完成
`CheckInService.checkIn()` 保存记录后显式 `flush()`，再调 `refreshDay()` 重算 `daily_records` 与 `plan_adherence`。
好处是「打卡成功 = 统计正确」，没有等待定时任务的时间窗；`plan_adherence` 写入失败只记 warn，不回滚整笔打卡。

### 4. 进阶闭环的安全闸门
`ProgressService.advice()` 的优先级：疼痛(1 天即 STOP) > 依从率 < 70% 或 RPE 偏高 1.0 → DELOAD > RPE 偏低 → SWAP > 依从率 ≥ 90% → PROGRESS > HOLD。
`advance()` 只有在决策为 `PROGRESS` 且 `canAutoApply=true` 时才真正生成下一版；其余情况返回 `newPlanId=null` 并说明原因——**不是缺陷，是刻意不让人在被压垮时继续加量**。

## 八、可复用的工程注意事项

1. **PS 5.1 会把 `"-h" "127.0.0.1"` 拆成两个参数**，host 只收到 `127` → 一律写 `"-h$DbHost"` 或整数组传入。
2. **edit/write 保存 .ps1 会丢失 UTF-8 BOM**，PS 5.1 随即按 GBK 解码报「字符串缺少终止符」/ 语法错 → 每次改完用 python 以 `utf-8-sig` 重存。
3. **`Start-Process -RedirectStandardOutput` 启动的 java 会随宿主脚本退出而掉线**（文件句柄失效）→ 用 `ProcessStartInfo` 交 `cmd.exe /c ... 1> 2>` 托管重定向。
4. **`mvn -q` 会掩盖编译失败**，看 `BUILD SUCCESS` 要用 `-B`；编译失败时 surefire 仍会打印旧用例结果，先确认 `target/classes` 时间戳。
5. **绝不使用 PowerShell 读写 Java/TS 源码**（GBK 解释 + 吞换行会导致乱码与语句粘连），一律用编辑工具或 python 显式 `utf-8`。
