# P3 改造说明：多轮对话与局部修订

> 对应《FitLife 现状分析与优化方案设计》P3 阶段（对话与修订）。
> 目标：清偿差距 G4（无多轮对话状态与局部修正）、G6（会话不留服务端），
> 使「图 3 场景」可演示：同一份计划在两轮对话内完成局部替换，且可回滚。

## 一、改造范围（五项）

| # | 改造项 | 清偿差距 |
|---|--------|---------|
| 1 | 会话与消息持久化（chat_session / chat_message） | G6 |
| 2 | 上下文装配（档案 + 当前计划 + 校验报告 + 最近 6 轮） | G4 |
| 3 | 意图路由（LLM 结构化优先，关键词规则兜底） | G4 |
| 4 | 局部修订（定位 → 替代 → 重算 → 校验 → v+1 落库 → Diff） | G4 |
| 5 | 幂等与回滚（revise 端点幂等回放 + activate 版本回滚） | G4 |

## 二、实现方式

### 1. 会话与消息持久化
- 新表 `chat_session`（session_key 唯一 / user_id / plan_id / title / last_active_at，idx_cs_user）与
  `chat_message`（session_id / role / content / action / tokens / refs，idx_cm_session），
  迁移脚本 `sql/migration/V3__p3_chat_revision.sql`（幂等，可重复执行）。
- `ChatSessionService`：findOrCreateSession 兼容前端 UUID session_key 与数字 id；
  appendMessage 用 TransactionTemplate 显式独立事务（外层业务回滚不丢留痕），
  全部 try-catch（留痕失败只 warn，不阻断业务）。
- `ChatService.stream()/chat()` 同步留痕：AI 伙伴页对话也落库（user + assistant 成对，
  action 记录 CHAT/REVISE 等），跨设备可查。

### 2. 上下文装配
- `ChatSessionService.assembleContext(userId, session)`：用户档案 + 当前 ACTIVE 计划
  （v{n} + 全动作列表含 id/rpe）+ 上次校验结论 + 最近 6 轮消息 → 拼成文本，
  供意图路由与后续 LLM 调用使用。
- 对话历史从「前端上报」升级为「服务端读取」；前端仍传 sessionKey 即可。

### 3. 意图路由（IntentRouter）
- 优先 LLM：completeGuarded（endpoint=INTENT_ROUTE，temp 0.1，maxTokens 300）
  输出结构化 JSON `{intent, operation, dayOfWeek, exerciseName, newRpe, replaceHint}`。
- 无 API Key / 解析失败 / 空 intent → 关键词规则兜底：
  生成|重新生成 → GENERATE；换|替换|改成 → OP_REPLACE；强度|RPE|累 → OP_ADJUST_RPE；
  去掉|删除 → OP_REMOVE；为什么|依据 → QUERY；其余 CHAT。
- REVISE 但无 ACTIVE 计划时升级为 GENERATE（不会对空计划做修订）。
- 正则提取目标动作名/替换提示，星期前缀自动剥离（“周一俯卧撑”→“俯卧撑”）。

### 4. 局部修订（PlanRevisionService，POST /api/plan/revise）
- 流程：resolveSession → assembleContext → route → 四分支（GENERATE/REVISE/QUERY/CHAT）。
- doRevise：对当前 ACTIVE 计划快照 → 三种操作：
  - OP_REPLACE：pickReplacement（提示名 contains > 同肌群 > 任意非禁忌，过滤伤病禁忌）→ 替换后 reSummarize 重算热量；
  - OP_ADJUST_RPE：clamp 4–9；
  - OP_REMOVE：删除目标动作（无替代）。
  → reSummarizeWeek → PlanValidator 校验（V3 环比基线 = 修订前周组数，防止局部修订误报容量超标）
  → persistAsNewVersion：旧 ACTIVE 置 ARCHIVED，新版本 version+1、parent_id、
  sourceLink=REVISED、changeNote="用户修订：..." → 结构化 Diff 返回。
- 动作定位 locate()：Round1 精确 equals；Round2 前向 contains（“深蹲”→“徒手深蹲”）；
  不做反向 contains（防止“去掉跪姿俯卧撑”误删“俯卧撑”）。
- 响应 `RevisePlanResponse`：action / reply / plan / diff（type: REMOVED|ADDED|MODIFIED +
  dayLabel + exerciseName + detail）/ sessionKey / intentByLlm / note。
- GENERATE 分支委托 PlanService.generatePlan(force=true)；QUERY 分支离线拼知识依据
  （校验报告 + 风险提示），不依赖大模型。

### 5. 幂等与回滚
- `/api/plan/revise` 挂 P1 的 @Idempotent 切面：同 key 同 body → 回放（响应头
  `Idempotent-Replay: true`，body 与首次完全一致，不重复落库）；同 key 异 body → 409。
- 修订产生的新版本可随时用 P2 的 `POST /api/plan/{id}/activate` 回滚。

### 前端（Plan.vue）
- 新增「对话式微调」卡片：输入框 + 四条快捷指令（替换/降强度/移除/重新生成），
  展示 reply、意图标签（是否走 LLM）、action 与 Diff 列表（ADDED 绿 / REMOVED 红 / MODIFIED 黄）。
- sessionKey 持久化到 localStorage（fitlife_revise_session），跨刷新保持同会话。
- api/index.ts：planApi.revise(data)（timeout 60s；POST 自动带 Idempotency-Key）。

## 四、对既有逻辑的影响
- 旧端点行为不变：/api/plan/generate、/chat、/ai/* 均走原链路；
  verify-p1 19/19、verify-p2 23/23 回归通过。
- ChatService 仅增加留痕调用（try-catch 包裹，留痕失败不影响原对话功能）。
- 修订落库复用 P2 版本链结构（version/parent_id/change_note/source_link），
  sourceLink 新增枚举值 REVISED，前端徽标显示「用户修订」。

## 五、回滚方式
- 代码回滚：恢复打包前源码即可（无破坏性数据结构变更）。
- 数据回滚：chat_session/chat_message 为纯新增表，DROP 不影响旧功能；
  修订产生的计划版本可用 activate 随时切回任意历史版本。

## 六、使用方式

```powershell
# 一键执行（迁移 + 构建 + 测试 + 启动 + 自检 + P1/P2 回归）
powershell -ExecutionPolicy Bypass -File scripts\p3-oneclick.ps1 `
    -DbPort 3307 -DbUser fitlife -DbPass yourpass -BackendPort 8090

# 只跑验收自检（服务已启动时）
powershell -ExecutionPolicy Bypass -File scripts\verify-p3.ps1 -BaseUrl http://localhost:8090

# 前端
cd FitLife-web && npm install && npm run dev
```

无 API Key 环境下：意图路由走关键词规则（intentByLlm=false），修订链路全部在
服务端规则层完成——这是设计内的合法降级路径，验收不依赖大模型。
