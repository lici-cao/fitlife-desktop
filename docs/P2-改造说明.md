# P2 改造说明 —— AI 计划生成主链路

> 阶段：P2（排期 3 周 / 15 人日，见《FitLife 现状分析与优化方案设计》表 13）
> 目标：清偿差距 G1（生成实为模板）、G2（无知识库与规则校验）、G3（无多轮修订引用）、
> G5（无计划版本链）、G11（AI 调用无可靠性与计量）。
> 原则：旧端点行为不变；新链路全部在 `PlanOrchestrator` 内完成；无 API Key 时走
> 模板降级分支，同样产出校验报告与版本链（`source_link=TEMPLATE`），属合法验收路径。

---

## 一、五项改造：范围 / 实现 / 验收标准

### 1. 运动处方知识库与规则入库

| 项 | 内容 |
| --- | --- |
| 改动范围 | 新表 `knowledge_item`（24 条种子：FITT/HR/PROG/REC/CI/SUB/TEC/POP）、`knowledge_rule`（6 条阈值规则，expression 为 JSON）；新文件 `entity/KnowledgeItem.java`、`entity/KnowledgeRule.java`、`repository/*Repository.java`、`service/KnowledgeRetriever.java`；只读管理端点 `controller/AdminController.java` |
| 实现方式 | 迁移脚本 `sql/migration/V2__p2_ai_pipeline.sql`（幂等：IF NOT EXISTS / INSERT IGNORE / information_schema+PREPARE，空操作分支 DO 0）。检索采用关键词打分（goal_scope +2、keywords 命中 +1 封顶 3、伤病+禁忌/替代类 +3），top8 注入 Prompt「必须遵守的约束」段并快照落库。规则阈值供校验器读取，读不到自动退内置默认——**规则表坏/空不阻断生成** |
| 验收标准 | ① 四张新表存在且种子 24/6/1；② 生成请求的 Prompt 含检索出的约束行；③ `plans.knowledge_snapshot` 落库；④ 普通用户访问知识端点 403、管理员 200；⑤ 规则 expression 非法 JSON 时校验器仍按默认工作（单测 `brokenRuleJsonFallsBack`） |

### 2. Prompt 模板版本化

| 项 | 内容 |
| --- | --- |

### 3. 规则校验器 + 最小修复器（六类校验）

| 项 | 内容 |
| --- | --- |
| 改动范围 | 新文件 `dto/ValidationReport.java`、`service/PlanValidator.java`、`service/PlanRepairer.java`；`util/BodyMetrics.java` 增心率静态段（HRmax=220−年龄、Karvonen 靶心率、RPE→%HRR 映射）；`user_profiles.hr_rest` 列 + `ProfileDTO/DataService` 透传；`PlanOrchestrator` 校验-修复循环 |
| 实现方式 | V1 靶心率（RPE→%HRR，>90% HRmax 储备 ERROR；初级 RPE≥8 每日聚合 WARN）；V2 FITT-VP（目标→天数/周有氧≥150min/大肌群频次）；V3 循序渐进（周总组数环比 >10% ERROR，基线=上一版）；V4 恢复间隔（同肌群相邻 <48h，双高 RPE ERROR 否则 WARN）；V5 禁忌（伤病 token 匹配动作 contraindication，ERROR）；V6 容量（单次 4-6 动作、超预算 15%、单肌群周组数 >20 WARN）。passed=无 ERROR；score=100−15×ERROR−5×WARN。修复器按违例最小改动：禁忌同肌群替代、RPE 压回上限、连日肌群降 RPE、减脂补有氧、超容量删尾部；≤2 轮重校验；每步动作写入 `change_note` |
| 验收标准 | ① 单测 22 项全绿（校验 10 + 修复 4 + 支撑 8，`mvn test` 真跑）；② 任意生成响应 `validationReport` 非空（score/checks/riskNotes）；③ 膝伤用户计划 0 个膝关节禁忌动作（G11）；④ `riskNotes` 恒含靶心率区间行；⑤ 报告持久化，detail 回读一致（G18） |

## 三、一键执行与验证

```powershell
# 全自动：迁移 V1+V2 → mvn package（含 22 项单测）→ 启动 → verify-p2 → verify-p1 回归
pwsh -File scripts\p2-oneclick.ps1

# 指定库与端口（本机 8080 被桌面版占用时用 8090）
pwsh -File scripts\p2-oneclick.ps1 -DbPort 3307 -DbUser fitlife -DbPass 888 -BackendPort 8090

# 只重跑验收（服务需在跑）
pwsh -File scripts\verify-p2.ps1 -BaseUrl http://localhost:8090

# 日常启动脚本已同步：自动执行 V1+V2 迁移
.\start-fitlife.ps1
```

脚本约定：`.ps1` 必须 UTF-8 BOM；HTTP 断言用 `System.Net.HttpWebRequest`（PS 5.1 下 4xx 可读体与头）；`-SkipDb/-SkipBuild/-SkipVerify/-SkipTests/-NoStart` 可分步跳过。

## 五、回滚方案

- 数据库：V2 只增表/增列，回滚即 `DROP TABLE knowledge_item, knowledge_rule, prompt_template, ai_call_log;` 与 plans 列可留不用（实体列全可空，旧 jar 可继续跑）。
- 代码：P2 未删除任何旧方法；`PlanService.generatePlan` 若需退回旧行为，把委托改回原实现即可（原实现见 git 历史 / 初改系统.zip）。
- 运行：无 Key 环境天然走模板降级，等价于 P1 行为 + 校验报告增强。

## 六、遗留与后续（P3 承接）

- 多轮对话「局部修订上一版」尚不可用：对话链路未接版本引用（P3 核心项）。
- 知识库检索为关键词打分，向量检索按计划留作可选项（报告排期约束允许）。
- 知识条目/规则的写入口（后台管理 CRUD）留给 P5；本期只读端点。
- `exercises.difficulty` TINYINT 与实体 Integer 的历史差异仍在（ddl-auto=validate 会报，现用 none/update 不受影响）。
